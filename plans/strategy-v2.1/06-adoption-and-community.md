# Adoption and Community

## Objective

Find a small number of developers with a real problem, help them succeed, and learn why they return. Do not optimize for broad attention before the product is understandable and useful.

## First external-user cohort

### Step 1 — Build a prospect list

Under Normal capacity, identify up to 20 prospects in small batches; Minimum starts with a few relevant contacts. Prioritize people who:
- Use Claude Code on established projects and already maintain fragmented instructions, skills/workflows and hooks.
- Maintain real projects with conventions and tests.
- Have discussed agent inconsistency, workflow control, or verification problems.
- Are willing to give candid feedback.

Use public technical communities and personal networks. Respect community rules; do not mass-post promotional messages.

### Step 2 — Personal outreach

Send a short, specific note explaining:
- The problem Lodestar is trying to solve.
- Why their workflow appears relevant.
- What the pilot asks them to do.
- That candid negative feedback is welcome.

Do not ask for stars as the primary call to action.

### Step 3 — Recruit up to five pilot users

Offer a 30–45 minute onboarding session if needed, but observe how much help is required. Ask users to run a task on their own project, not a prepared showcase repository only.

Apply [capacity limits](04-roadmap-12-months.md): start with one observation in Minimum mode, expand only when support fits the weekly ceiling. State supported versions, upgrade/removal steps and reporting channels before onboarding. Outreach messages are sent by the owner or an explicitly authorized agent; the strategy itself is not permission to contact people.

### Step 4 — Convert feedback into product decisions

Maintain a simple feedback log:
- User and project context (only what they consent to share).
- Task attempted.
- Where they got stuck.
- What worked.
- Workarounds used.
- Feature requests.
- Whether they returned.
- Follow-up action and owner.

Group feedback by repeated problem, not by loudest request.

### Step 5 — Ask for a second use

A second independent use is stronger evidence than a positive first impression. Ask whether the user would use Lodestar on another task and what would prevent that.

Record actual task dates, not intent alone. Separate early repeat in days 1–29 from retained use in days 30–60, using [07](07-metrics-and-sustainability.md). Report nonresponse and assisted use instead of treating them as independent success.

## Content strategy

Publish useful engineering material:
- A short “why this exists” explanation.
- A real walkthrough of a bug fix, feature, or refactor.
- A comparison with a strong lightweight instructions baseline.
- Benchmark methodology and honest results.
- Lessons from pilot failures.
- Integration guides for supported runtimes.

Every article should teach something even if the reader never installs Lodestar.

## Channel strategy

Prioritize channels where target users already discuss AI coding workflows:
- GitHub issues and discussions.
- Relevant Reddit communities, following their rules.
- Hacker News when there is a substantive technical story.
- X or technical blogs for progress and findings.
- Existing developer communities and direct conversations.

Do not create a Discord server until there is sustained demand for real-time community interaction. A quiet Discord creates maintenance overhead without proving adoption.

## Contribution funnel

1. User can install and complete a task.
2. User can report a reproducible issue.
3. User can improve docs or examples.
4. User can maintain a tested example or improve an existing workflow/capability; additions still need a demonstrated problem.
5. User can review or maintain an area.

Make the first contribution small and well-scoped. Document expected checks and review standards.

## Adoption principles

- Be transparent about limitations and unsupported environments.
- Never manufacture testimonials or imply pilot users endorse the project.
- Do not equate downloads or stars with active usage.
- Ask permission before publishing user names, project names, quotes, or results.
- Prefer repeat usage and independent contributions over launch-day traffic.
- Contribution counts are not a retention gate. Encourage adaptation and shareable examples while keeping the open-source core useful without a commercial service.
